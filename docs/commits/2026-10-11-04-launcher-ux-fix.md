## 1. 本次提交的目标

**要解决的问题（已实际发生）**

用户双击桌面快捷方式时，看到 `Press any key to continue . . .` 且无法判断该输入什么。
根因链：

1. 服务已在运行（3000 端口被占）；
2. `scripts/launch.mjs` 检测到健康实例后 `process.exit(0)`；
3. `启动.cmd` 无法区分「已有实例」与「正常停止」，一律打印 **「服务已正常退出。」** —— 与实际状态矛盾；
4. 脚本末尾的 `pause` 无条件执行，弹出 `Press any key to continue . . .`。

**可验收目标（DoD）**

| 编号 | 目标 | 验收标准 |
| --- | --- | --- |
| U1 | 非错误路径不再阻塞 | 「已有实例」与「正常停止」两种情况均不需要按键，窗口自动关闭 |
| U2 | 状态提示与事实一致 | 「已有实例」时输出「服务已在运行，控制台已打开」，不再出现「已正常退出」 |
| U3 | 错误路径仍保留暂停 | 启动失败（缺 Node / 缺依赖 / 端口冲突）时仍 `pause`，便于阅读错误 |
| U4 | 退出码可区分 | 已有实例 = `3`，正常停止 = `0`，失败 = 其他非零 |
| U5 | 部署副本与压缩包同步 | 桌面副本与 `微信AI接入网关-v1.0.0.zip` 内的启动脚本均为修复后版本 |

**明确不在本次范围**

- 让服务常驻后台（进程守护 / Windows 服务）
- 托盘图标、开机自启
- 打包体积优化（承接计划 03 附 C）

## 附 A. 验证证据（已回填 · 2026-10-11 实测）

**先复现问题**（旧版部署副本，服务正在运行）：

```
退出码=0  含Press any key=True
末两行: 服务已正常退出。 / Press any key to continue . . .
```

→ 与用户反馈完全一致，根因确认。

**修复后四条分支实测**：

| 分支 | 场景构造 | 退出码 | 含 `Press any key` | 输出要点 | 结论 |
| --- | --- | --- | --- | --- | --- |
| A 已有实例 | 服务运行时执行 `启动.cmd` | **3** | **否** | 「检测到服务已在运行」→「服务已在运行，管理控制台已打开。本窗口 3 秒后自动关闭。」 | ✅ |
| E 正常停止 | 启动就绪后结束服务进程 | **0** | **否** | 「服务已停止。本窗口 3 秒后自动关闭。」，cmd 窗口 `HasExited=True` | ✅ |
| C 缺少 Node | 临时目录无 `runtime` 且 PATH 无 node | **1** | 是（保留） | 「[错误] 未找到 Node.js 运行时。」+ 两种解决方式 | ✅ |
| D 缺少依赖 | 有 Node、无 `node_modules`、无实例 | **1** | 是（保留） | 「开发环境请执行：npm install」 | ✅ |
| F 端口被占 | 占位服务监听 3000 | **1** | 是（保留） | 「[失败] 服务在就绪前退出（退出代码 1）」+ 三类排查指引 | ✅ |

**其他验证**

| 验证项 | 结果 |
| --- | --- |
| 构建回归 `npm run build` | `✓ built`，exit **0** ✅ |
| 冒烟回归 `verify-wechat.mjs` | **31 项通过 / 0 失败** ✅ |
| 部署副本同步 | `启动.cmd` 与 `scripts/launch.mjs` 哈希比对 **一致** ✅ |

**本轮修复中新增发现的缺陷（一并修复）**

> **正常停止被误判为启动失败**：原先 `child.on('exit', code => process.exit(code ?? 0))` 直接透传子进程退出码。
> 无论 Ctrl+C 还是强制结束，被终止进程的退出码均非 0，导致 `启动.cmd` 走 `:failed` 分支，
> 打印「[失败] 启动未成功」并 `pause` —— 与「服务已正常停止」的事实矛盾。
> 已改为用 **`becameReady`（是否曾探测到健康实例）** 作为判据：曾就绪 → 退出码 0（停止）；就绪前退出 → 退出码 1（失败）。
> 另修正失败提示中未定义变量 `%PORT%` 导致的空文本，并把失败指引细化为「缺依赖 / 缺 Node / 端口被占」三类。
