# 微信 × DeepSeek 自动回复集成方案设计

> 版本 v1.0 · 2026-10-12 · 状态：**待决策**（见 §8）
> 说明：本文档中的第三方接口路径与字段基于通行用法整理，**实施时须按对应平台官方文档核对最新版本**。

---

## 0. 结论摘要

1. 目标「接收**个人微信好友**消息并自动回复」**无法通过官方接口实现**：微信未开放个人号机器人 API。官方开放能力仅覆盖 公众号 / 企业微信 / 微信客服 / 小程序客服（见 §1.1）。
2. **非官方方案（协议逆向、客户端注入 hook）不在本方案范围内**，不实现、不引入依赖，原因见 §1.3。
3. 推荐两条合规落地路径：
   - **路径 A（推荐）企业微信自建应用**：可接收成员与**外部联系人（含微信用户）**消息，支持主动推送、图片/文件媒体下载 —— 功能上最接近「好友消息自动回复」。
   - **路径 B 公众号增强**：本项目已实现，补齐人设/绑定/媒体即可。
4. 本项目现有架构（`WeChatChannel` 通道路由表 + `AIProvider` 提供方注册表 + 会话/上下文/指令/日志）已为多通道预留扩展点，**新增渠道是增量工作**，不需要重构。
5. 需求 3–5 中的「5 种人设、身份绑定、指令规范、出站重试与日志」属**通道无关能力**，可先行实施并立即在公众号通道生效。

## 1. 连接目标（需求 1）

### 1.1 官方开放能力边界（事实）

| 渠道 | 可接收的消息来源 | 主动推送 | 被动回复时限 | 媒体能力 |
| --- | --- | --- | --- | --- |
| 个人微信 | — **无开放接口** | — | — | — |
| 公众号（服务号） | 关注者发给公众号的会话消息 | 客服消息 | 5 秒 | 素材/临时素材上传下载 |
| **企业微信自建应用** | 成员、**外部联系人（可含微信用户）** | 应用消息 | 5 秒 | `/cgi-bin/media/get` 下载 |
| 微信客服 | 用户在微信内发起的咨询 | 客服消息 | 5 秒 | 支持 |
| 小程序客服 | 小程序内用户消息 | 客服消息 | 5 秒 | 支持 |

### 1.2 目标映射

| 你的原始目标 | 可达成形态 | 结论 |
| --- | --- | --- |
| 接收好友消息 | 接收**外部联系人/客户**消息（企业微信）或关注者会话消息（公众号） | ⚠️ 等价替代 |
| 自动回复 | 官方被动回复 + 主动推送 | ✅ |
| 用 DeepSeek API-Key 回复 | 复用现有 OpenAI 兼容提供方（baseUrl=`https://api.deepseek.com/v1`，model=`deepseek-chat`） | ✅ 已支持 |
| 设置 5 种人设 | 人设注册表 + 会话级绑定 + 指令切换（§4.3） | ✅ 待实施 |
| 文本/图片/链接消息 | 见 §2.3 | ✅ 待实施 |

### 1.3 明确不做：个人微信自动化

- 手段类别：个人微信协议逆向、微信客户端注入/函数劫持、网页版协议复用、模拟登录等（俗称外挂/hook）。
- 不做原因（如实说明）：
  1. **违反平台规则**：触发《微信个人帐号使用规范》红线，账号会被限制或封禁 —— 你的目录名已注明该风险；
  2. **法律风险**：涉及对第三方客户端的非授权改造与协议逆向，存在合规争议；
  3. **不可维护**：依赖客户端版本，随时失效且无官方支持。
- 因此：本项目**不新增**该类依赖、不提供该类代码与配置。若需要「他人发消息给 AI 自动回」的体验，请采用 §1.1 中的官方渠道。

## 2. 消息通道设计（需求 2）

### 2.1 复用现有通道抽象

```
server/wechat/types.ts      → WeChatChannel 接口
  verify()            服务器校验（GET）
  parse()             报文解析 → 归一化 InboundMessage
  buildPassiveReply() 被动回复报文
  canPush()/push()    主动推送
server/wechat/index.ts      → 渠道注册表 + 统一管线
  去重 → 会话解析 → 意图/指令 → 上下文装填 → AI 调用 → 落库 → 回复下发
```

新增渠道 = 新增一个实现 `WeChatChannel` 的文件 + 在注册表登记；**管线、上下文、AI、日志、控制台均无需改动**。

### 2.2 各渠道实现规格

| 维度 | 公众号（已完成） | 企业微信自建应用（待实施） | 微信客服（后续） |
| --- | --- | --- | --- |
| 服务器校验 | `sha1(sort(token,timestamp,nonce))` | `sha1(sort(token,timestamp,nonce,echostr))` | 同企业微信 |
| 报文加密 | 明文模式（当前） | **AES-256-CBC + Base64（EncodingAESKey）必选** | AES 必选 |
| 消息体 | XML | XML（含 `<Encrypt>`） | JSON 回调 |
| 凭据 | AppID + AppSecret | **CorpID + AgentId + Secret** | CorpID + Secret |
| access_token | `/cgi-bin/token` | `/cgi-bin/gettoken` | 同企业微信 |
| 主动推送 | `/cgi-bin/message/custom/send` | `/cgi-bin/message/send`（需 agentid） | 客服消息接口 |
| 媒体下载 | 素材接口 | `/cgi-bin/media/get` | 支持 |
| 关键难点 | — | **AES 加解密 + 4 元素签名** | 同上 |

> 实施要点：企业微信必须实现 AES 解密与「回复也需加密」，比公众号明文模式复杂，是本次工作量的主要部分。

### 2.3 消息类型支持（文本 / 图片 / 链接）

| 类型 | 接收处理 | 回复策略 |
| --- | --- | --- |
| 文本 | 直接进入管线 | 文本回复（超长自动截断，已有） |
| 图片 | 解析 `PicUrl` / `MediaId` → **下载并存档**（落 `wx_messages.raw` + 可选本地目录）；可选接入多模态理解 | 默认文字兜底；启用多模态后按图片内容回答 |
| 链接 | 解析标题/描述/URL，拼成上下文文本 | 按内容回答 |
| 语音/位置/其他 | 归一化为描述文本 | 文字兜底（已有） |

**图片策略三选一（§8 D4）**：① 下载存档 + 文字兜底（默认，成本最低）；② 接入多模态模型理解图片；③ 仅回提示「暂不支持」。
> 注意：DeepSeek 当前以文本为主，若要图片理解需另配多模态提供方 —— 提供方注册表已支持多模型并存。

### 2.4 可靠性设计

- **入站**：消息去重（已有，5 分钟 TTL）+ 优先异步推送（规避 5 秒被动回复超时）
- **出站**：失败重试 3 次，指数退避 1s/2s/4s；仍失败则落库 `status=error` 并记日志
- **凭据**：`access_token` 内存缓存（提前 5 分钟过期刷新）；40164/40001 等错误码触发强制刷新并重试一次
- **网络中断**：启动自检（探测 access_token 是否可获取）+ 概览页状态标记；连续失败 N 次写入 error 日志

## 3. 用户身份识别与绑定（需求 3）

### 3.1 三级标识

```
渠道账号 ID（openid / userid / external_userid）
        ↓ 一对一会话
wx_conversations（已有）          会话与上下文、SDK session、用量
        ↓ 可选绑定
app_users + bindings（新增）      项目侧用户身份，用于跨渠道识别与权限
```

### 3.2 绑定流程（双向确认，防冒绑）

1. 控制台「对话记录 → 生成绑定码」，得到 6 位一次性码（**10 分钟有效**）；
2. 用户在微信/企业微信发送：`绑定 8K2F9C`；
3. 后端校验有效性 → 写入 `bindings` → 回复「绑定成功，当前身份：张三」；
4. 解绑：发送 `解绑`，或控制台操作。

> 未绑定用户默认仍可对话（归属「匿名」），是否强制绑定由开关控制（§8 D3）。

### 3.3 数据模型（新增两张表，均为 `CREATE TABLE IF NOT EXISTS`，不影响既有数据）

```sql
app_users (
  id TEXT PRIMARY KEY, name TEXT NOT NULL, note TEXT,
  status TEXT NOT NULL DEFAULT 'active', created_at TEXT NOT NULL
);
bindings (
  id TEXT PRIMARY KEY,
  user_id TEXT NOT NULL,
  channel TEXT NOT NULL,
  external_user_id TEXT NOT NULL,
  bind_code TEXT, code_expires_at TEXT,
  bound_at TEXT NOT NULL,
  UNIQUE (channel, external_user_id)
);
```

## 4. 指令与事件（需求 4）

### 4.1 指令规范

统一「`/指令`」写法，并保留自然语言别名（对普通用户友好）：

| 指令 | 别名 | 作用 | 权限 |
| --- | --- | --- | --- |
| `/帮助` | `帮助`、`help` | 指令与人设说明 | 全部 |
| `/重置` | `重置`、`清空`、`新对话` | 清空上下文 | 全部 |
| `/人设` | `人设` | 列出 5 种人设 | 全部 |
| `/人设 N` | `切换人设 N`、`换成幽默` | 切换本会话人设 | 全部 |
| `/人设 默认` | — | 恢复全局默认人设 | 全部 |
| `/绑定 CODE` | — | 绑定项目账号 | 全部 |
| `/解绑` | — | 解除绑定 | 已绑定 |
| `/状态` | — | 查看当前人设/上下文条数/绑定身份 | 全部 |

解析规则：**先匹配指令表，未命中再按普通对话处理**（现有 `intent` 阶段扩展）。

### 4.2 事件

| 事件 | 处理 |
| --- | --- |
| 关注/订阅 | 欢迎语（已有） |
| 菜单/按钮点击 | 映射为指令（如点击菜单「切换人设」） |
| 入群/被移除 | 记日志，不回复 |
| 回调重试 | 去重命中 → 直接返回成功（已有） |

### 4.3 5 种人设设计（提案，可改）

| # | 名称 | 语气与定位 | 默认系统提示词（要点） | 开场白 |
| --- | --- | --- | --- | --- |
| 1 | 温柔知心 | 温暖、共情、耐心 | 先共情再接话，语气柔和，不评判，多用短句 | 「我在的，慢慢说～」 |
| 2 | 专业顾问 | 严谨、结构化、给方案 | 结论先行，分点说明，必要时给取舍与风险 | 「说下背景，我给你拆解。」 |
| 3 | 幽默损友 | 轻松、会接梗、适度吐槽 | 口语化，可调侃但不冒犯，禁止攻击性表述 | 「说吧，又整啥活了？」 |
| 4 | 高效助理 | 极简、可执行 | 直接给结果与下一步，不铺垫，必要时列 checklist | 「目标是什么？直接说。」 |
| 5 | 毒舌吐槽 | 犀利、有趣、有分寸 | 可以吐槽现象但不对人；不涉及外貌/身份/敏感话题 | 「行，我听着呢。」 |

**人设实现方式**

- 每种人设 = 一条 `system prompt` 模板（含语气、边界、禁用项）；
- 三层优先级：`会话级人设` > `用户级默认人设` > `全局默认人设`；
- 全局默认与用户默认均可在控制台配置（复用现有「API-Key 配置 → 系统提示词」区域，改为「人设管理」）；
- 与 DeepSeek 的关系：DeepSeek 接口无状态，**上下文由本项目维护**（已有 `maxContextMessages` 窗口 + 落库），人设只是每次请求的 system prompt，不增加调用成本。

## 5. 异常与日志（需求 5）

### 5.1 错误分类与处置

| 类别 | 典型表现 | 处置 |
| --- | --- | --- |
| 网络超时/中断 | fetch 超时、ECONNRESET | 出站重试 3 次（指数退避）；入站不重试（微信会重试 + 去重兜底） |
| 限流 | HTTP 429 | 退避后重试；记录 warn |
| 服务端错误 | 5xx | 重试；连续 3 次失败标记提供方异常 |
| 凭据失效 | 40001/42001/40164 | 强制刷新 access_token 并重试 1 次 |
| 签名/解密失败 | 校验不通过 | 拒绝处理 + warn 日志（含来源 IP） |
| 媒体下载失败 | 404/超时 | 降级为文字提示，不阻断对话 |
| 主动推送失败 | errcode≠0 | 落库 `status=error`；必要时回退被动回复 |

### 5.2 日志与可观测性（复用现有能力）

- 分级日志落库 `app_logs`（已有），并**新增 `request_id` 贯穿一次消息处理**（入站→AI→出站），便于串联排查；
- 每次收发均落 `wx_messages`（含 `provider/model/latency_ms/status/error`，已有）；
- 控制台「运行日志」页支持级别过滤与详情展开（已有）；「运行概览」展示错误计数与提供方状态（已有）；
- **告警**：连续失败 ≥N 次（默认 5）时写入 error 日志，并在概览页高亮横幅。

### 5.3 出站重试实现要点

```
pushWithRetry(inbound, text, settings):
  3 次尝试；1s / 2s / 4s 退避
  每次失败：记 warn(errorCode)
  最终失败：抛错 → 管线捕获 → 落库 status=error → 若为被动回复模式则改用被动回复兜底
```

## 6. 部署与配置（需求 6）

### 6.1 新增配置项（控制台可视化 + `.env` 兜底）

| 分组 | 字段 | 说明 |
| --- | --- | --- |
| 企业微信 | `corpId` / `agentId` / `secret` / `token` / `encodingAESKey` | 自建应用凭据 |
| 微信客服 | `corpId` / `secret` / `token` / `encodingAESKey` | 后续阶段 |
| DeepSeek | 复用「OpenAI 兼容」：`baseUrl=https://api.deepseek.com/v1`、`model=deepseek-chat`、`apiKey` | **密钥请在控制台录入，勿贴在聊天/代码中** |
| 人设 | `defaultPersonaId`、5 条人设提示词 | §4.3 |
| 绑定 | `requireBinding`、`bindCodeTtlMinutes` | §3 |
| 可靠性 | `pushRetryTimes`、`pushBackoffBaseMs`、`alertErrorThreshold` | §5 |

### 6.2 公网与域名要求

- 回调 URL 必须 **HTTPS**（企业微信/公众号均要求），且为 443 或 80 端口；
- 企业微信需配置**可信域名 / 可信 IP**；公众号需配置服务器地址与 IP 白名单（如启用）；
- 建议：Nginx 反代 → 本服务 3000；仅暴露 `/wechat`（及必要的管理入口），管理接口置于内网或加 `ADMIN_TOKEN`。

### 6.3 长期稳定运行

| 项 | 建议 |
| --- | --- |
| 进程守护 | NSSM 注册为 Windows 服务，或 `pm2`；失败自动重启 |
| 健康检查 | 定时 `GET /api/health`；异常告警 |
| 日志轮转 | `app_logs` 按保留天数清理（新增定时任务，默认 14 天） |
| 数据备份 | 定时复制 `data/chat.db`（含 WAL 检查点）；保留 7 份 |
| 配置备份 | 控制台配置导出为 JSON（新增按钮） |
| 安全 | `ADMIN_TOKEN` 必开；密钥不落日志（已有脱敏）；数据库文件权限收紧 |

### 6.4 上线检查清单

- [ ] 渠道凭据（CorpID/Secret/Token/AESKey 或 AppID/AppSecret）已在控制台保存并通过「连通性测试」
- [ ] 回调 URL 校验通过（GET 返回 echostr）
- [ ] 发送测试消息 → 收到 AI 回复
- [ ] `/人设` `/重置` `/绑定` 指令验证通过
- [ ] 主动推送失败重试与错误落库验证（可断开网络模拟）
- [ ] `ADMIN_TOKEN` 已设置，管理接口不可匿名访问
- [ ] 数据备份与日志清理任务已配置
